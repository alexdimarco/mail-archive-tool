**Verdict: HIGH_FRICTION_NOT_SHIPPABLE** — still, and for fewer reasons. Two high-friction cells remain and each is an owner decision, not wording: **CA-3 (F1, ESC-MS2-4)**, where a plain-text message with a base64 label its text does not honour is shown as mojibake, search no longer finds its words and a `-mode full` re-run replaces an older archive's readable page with the garbled one; and **OW-11 (F4, MC20)**, where a cut or boundary-less message in a mailbox file keeps the posture WARN for good. The fix pass made the words around both true and followable (the CA-3 row no longer names a `.partial` file in a zip that does not exist; the OW-11 remedy now says what cures a cut message, and that a message malformed as sent stays listed), but it did not change the page of CA-3 or the posture of OW-11. **F2 (ESC-MS2-2)** also waits: its exact counts and sentences are proposed below, and it was not built because it edits three existing MA-348 assertions. Ship needs the owner's decision on F1 and F4, and a decision on whether F2's assertion edits are accepted; the rest of the in-scope Type III list is built. Why F1 blocks ship like a security finding: the walker's own promise is "never worse than v1" (P13), and for this class of message it is.

**Rationale (as walked at `0e3240d`; the fix pass changes the table's last column, not this paragraph).** The mechanism itself holds up under real files. A message with a made-up charset and a later attachment keeps both (OW-1). An unknown transfer encoding and a damaged or cut base64 part are kept as `.undecoded` and `.partial` in the zip, each with a report row that has a why and a what-to-do, a Verification line, a `status` line and the same number in `status -json` (OW-2). The cut attachment fills on the next run once the mailbox file holds the complete message, in one step, and the second run says `filled=1` and `Incomplete: none` (OW-3). An upgrade does not churn: eight good records were skipped, the two gap records were re-read and filled (OW-6). With 500 messages and 3 gaps the summary is one proportionate line, the posture does not move and the CLI line, `status`, `status -json` and the report agree on 3 (CA-1). Hostile attachment names keep the control characters and reserved names out of the zip, and the report row strips bidi controls (IN-2).

The friction is in what the words and the counts claim. The "cannot decode" count (7 of 10 messages in archive A) takes in the fallback record, an unsplit multipart and a corrupt body, and every surface says each is "kept as received in the attachments zip": three of the seven have no part and no zip (ESC-MS2-2, F2). The fallback message is counted there and again on its own line. Four of the seven are also in "still missing content", so the three counts on one screen add up to 12 for 10 messages, and the missing-content remedy that follows ("download for offline use … IMAP / Outlook offline window") is printed for a file on disk (F3). An inheritor's `README.txt` says every fillable or terminal row "is missing from this archive" and never names `.undecoded` or `.partial`, while the message page says nothing at all about a cut-short part (F7, F8). An unsplit or corrupt message in a local mailbox file keeps the posture WARN for good, with a remedy that cannot be followed (F4).

Type II items (F1, F4, and F10's ESC-MS2-3 half) are owner decisions. The Type III items are buildable-away; all but F10 are this branch's own surfaces. **ESC-MS2-2 was not built.** The counts and sentences it would change are pinned by existing MA-348 assertions, so per the brief the proposal is in F2 and the build stops there. Everything else in scope was built in the fix pass below.

## Findings

In this branch's scope first, most valuable first; then the one Type I item and the out-of-scope ones.

**F1 · [Type II · in scope · cells CA-3, OW-6 · ESC-MS2-4, judged · DEFERRED TO THE OWNER, see Status] The "fidelity contains v1" waiver is message-wide, so one note turns a readable body into noise.**
`holdsV1` skips the verbatim-body check for every body when any body-decoding note exists (`differs`). Walked: S10, a plain-text body with an unknown charset and a base64 label the text does not honour. The walker base64-decodes it, notes `charset-fallback`/`continued-after-error`, and the check lets it through. Owner-visible effects: the page is noise, search misses it, the row's claims are false (F6), the posture asks for a download that cannot help, and a full re-run of an older archive overwrites the readable page. This is the friction the escalation asked to be judged: it is high, and reducible without weakening the control (the notes already say which part they touched).
*Change (owner decision):* record which body a note touched; apply v1's verbatim rule to every body no note touched; a message that fails goes to v1 with the visible fallback gap, which is exactly what the S10 page would then read. The design text (4.2 step 3a) already words the waiver per body ("no body-decoding note touches it"), so this may be conformance rather than a change. It moves more messages into the fallback, which F2 makes honest.
*Status (fix pass): not built, and the proposed change is not enough.* In the walked message (`text/plain; charset="x-unknown"`, `Content-Transfer-Encoding: base64`, a sentence of plain text) there is ONE body, and every note the walker records (`continued-after-error`, `corrupt-part`, `charset-fallback`) is about that body, so "record which body a note touched and apply v1's rule to every body no note touched" leaves this body waived and the page unchanged (re-walked at `393b0a4`: the page is still `>Wš±ç…`, search still misses the sentence). The per-body narrowing is still worth doing as conformance with design 4.2 step 3a, for a message that has a second, untouched body. What would repair the cell is a rule about the decoding itself, and that changes S3b: a body whose declared base64 stops being base64 at its first line (the text holds characters outside the alphabet and white space, as plain text does) is read as not base64 (shown as sent, with a note), instead of "decode as far as it goes and keep the readable start". It moves S3b's damaged-body behaviour, so it is a design change for the owner, not a small fix inside the design. The fix pass built F6, so the row at least no longer names a file that does not exist, and left the page alone.

**F2 · [Type III · in scope · cells OW-2, OW-4, OW-7, CA-1, CA-2 · ESC-MS2-2, proposal; NOT built] The "cannot decode" count and its sentence are untrue for fallback, unsplit and corrupt-body records, and the fallback is counted twice.**
In archive A: S2, S3, S3b, S9b, S10, S9 and S4 are the "7". Of them S4 (fallback) has no part and no zip, S9 (unsplit) is shown as text, S10 (corrupt body) has no `.partial`. Every surface says "kept as received in the attachments zip" (CLI summary "(kept as received; see the report)", status's explanation line, `status` reason text, the GUI's "the files are in each message's attachments zip", README.md line 692). The same fallback record is also the "1 … kept as an earlier version read them".
