> As of 2026-10-12, walked against `wip/mf-s2-fric` at `0e3240d` (change set

> the `mailarchive` CLI built from that tree on macOS, and the CLI built from `dabed86`
> (parse scheme 1) for the upgrade cell. Method: the assurance-kit friction review, each
> cell an actor x scenario walked by typing the commands and reading the output, classified
> Type I (the ceremony is the control), Type II (design choice, reducible without weakening
> the control), Type III (missing legibility or tooling). Every command ran with HOME and
> the per-user config folders in a scratch home; the scratch mboxes were written by small
> Python scripts (no real mail, no network): ten messages of the shapes the scenarios name
> (archive A), 500 messages with three decode gaps (B), the truncated-attachment message
> alone and then complete (C), sender-chosen names that look like the tool's labels (D),
> undecodable parts with hostile names (E) and a depth-33 message that also carries a
> uuencoded file (F). The scripts and transcripts were kept outside the repository. Nothing

**Cells walked:** 17 &nbsp;·&nbsp; **Functioning:** 6 yes / 10 partial / 1 no &nbsp;·&nbsp; **High-friction cells:** 3 (CA-3, OW-11, IN-1) &nbsp;·&nbsp; **Findings:** 16 — Type I: 1 · Type II: 2 (2 in scope; F10 holds a third, ESC-MS2-3, judged and left to S7) · Type III: 13 (11 in scope)

**Verdict: HIGH_FRICTION_NOT_SHIPPABLE** — until the owner decides ESC-MS2-4 (F1) and the in-scope Type III legibility backlog below (F2, F3, F5 to F9, F11, F12, F14) is built, with F4's decision recorded. The verdict is carried by one Type II finding, not by the ceremony around it: with the walker on, a message the earlier parser showed readably (plain text, a made-up charset label, a base64 label the text does not honour) is shown as mojibake by this build; the report row that should explain it says "only the readable start is shown" and names a `.partial` file in a zip that does not exist; search no longer finds the words; and a `-mode full` re-run silently replaces the readable page of an older archive with the garbled one. That is a usability regression against the walker's own "never worse than v1" promise (P13), so it blocks ship like a security one. The rest is wording and counts.

**Rationale.** The mechanism itself holds up under real files. A message with a made-up charset and a later attachment keeps both (OW-1). An unknown transfer encoding and a damaged or cut base64 part are kept as `.undecoded` and `.partial` in the zip, each with a report row that has a why and a what-to-do, a Verification line, a `status` line and the same number in `status -json` (OW-2). The cut attachment fills on the next run once the mailbox file holds the complete message, in one step, and the second run says `filled=1` and `Incomplete: none` (OW-3). An upgrade does not churn: eight good records were skipped, the two gap records were re-read and filled (OW-6). With 500 messages and 3 gaps the summary is one proportionate line, the posture does not move and the CLI line, `status`, `status -json` and the report agree on 3 (CA-1). Hostile attachment names keep the control characters and reserved names out of the zip, and the report row strips bidi controls (IN-2).

The friction is in what the words and the counts claim. The "cannot decode" count (7 of 10 messages in archive A) takes in the fallback record, an unsplit multipart and a corrupt body, and every surface says each is "kept as received in the attachments zip": three of the seven have no part and no zip (ESC-MS2-2, F2). The fallback message is counted there and again on its own line. Four of the seven are also in "still missing content", so the three counts on one screen add up to 12 for 10 messages, and the missing-content remedy that follows ("download for offline use … IMAP / Outlook offline window") is printed for a file on disk (F3). An inheritor's `README.txt` says every fillable or terminal row "is missing from this archive" and never names `.undecoded` or `.partial`, while the message page says nothing at all about a cut-short part (F7, F8). An unsplit or corrupt message in a local mailbox file keeps the posture WARN for good, with a remedy that cannot be followed (F4).

Type II items (F1, F4, and F10's ESC-MS2-3 half) are owner decisions. The Type III items are buildable-away; all but F10 are this branch's own surfaces. **ESC-MS2-2 was not built.** The counts and sentences it would change are pinned by existing MA-348 assertions, so per the brief the proposal is in F2 and the build stops there.

## Findings

In this branch's scope first, most valuable first; then the one Type I item and the out-of-scope ones.

**F1 · [Type II · in scope · cells CA-3, OW-6 · ESC-MS2-4, judged] The "fidelity contains v1" waiver is message-wide, so one note turns a readable body into noise.**
`holdsV1` skips the verbatim-body check for every body when any body-decoding note exists (`differs`). Walked: S10, a plain-text body with an unknown charset and a base64 label the text does not honour. The walker base64-decodes it, notes `charset-fallback`/`continued-after-error`, and the check lets it through. Owner-visible effects: the page is noise, search misses it, the row's claims are false (F6), the posture asks for a download that cannot help, and a full re-run of an older archive overwrites the readable page. This is the friction the escalation asked to be judged: it is high, and reducible without weakening the control (the notes already say which part they touched).
*Change (owner decision):* record which body a note touched; apply v1's verbatim rule to every body no note touched; a message that fails goes to v1 with the visible fallback gap, which is exactly what the S10 page would then read. The design text (4.2 step 3a) already words the waiver per body ("no body-decoding note touches it"), so this may be conformance rather than a change. It moves more messages into the fallback, which F2 makes honest.

**F2 · [Type III · in scope · cells OW-2, OW-4, OW-7, CA-1, CA-2 · ESC-MS2-2, proposal; NOT built] The "cannot decode" count and its sentence are untrue for fallback, unsplit and corrupt-body records, and the fallback is counted twice.**
In archive A: S2, S3, S3b, S9b, S10, S9 and S4 are the "7". Of them S4 (fallback) has no part and no zip, S9 (unsplit) is shown as text, S10 (corrupt body) has no `.partial`. Every surface says "kept as received in the attachments zip" (CLI summary "(kept as received; see the report)", status's explanation line, `status` reason text, the GUI's "the files are in each message's attachments zip", README.md line 692). The same fallback record is also the "1 … kept as an earlier version read them".
*Proposal, exact.* Count each record once, in the first bucket its gaps fall in:
- **cannot decode** = a record with at least one gap of kind `undecoded-part`, `corrupt-part` or `structure-limit` (A in the walk: S2, S3, S3b, S9b, S10 = 5). `status -json` `undecodable` = this count.
- **shown as one text** = `unsplit-multipart` with no gap of the first kind (S9 = 1). New line, new additive field `unsplit_multipart`.
- **kept as an earlier version read them** = `fidelity-fallback` (S4 = 1), its own line as today, not in the first count. `fidelity_fallback` unchanged.
- `identity-stub` is not counted on any run or status surface (it is a report row; the page shows this version's reading, nothing is missing).
Wording (the pinned sentences stay; they become true):
- CLI Verification: `…, 5 message(s) with parts this version cannot decode (kept as received; see the report)` · new `…, 1 message(s) whose parts could not be told apart (shown as one text on the page; see the report)` · the fallback line `Verification: 1 message(s) kept as an earlier version read them, because this version could not decode them in full (everything that version read is kept)` — "nothing is lost" is true only against the earlier version, and a part only the walker would have kept is not kept (OW-4, reasoned).
- `status`: `Incomplete: 4 still missing content · 0 source-empty (never fillable) · 5 with parts this version cannot decode · 0 not yet re-examined` and its unchanged explanation line; a new `Shown as text: 1 message(s) whose parts could not be told apart — see <report>`; `Fallback:` unchanged except the same parenthesis. Rename the label from `Incomplete:` only if the owner prefers; the cost is every existing assertion on that string.
- GUI: `Kept as received, because this version cannot decode a part of them: 5 (the files are in each message's attachments zip)` unchanged; new `Shown as one text, because their parts could not be told apart: 1`.
- `status -json` `last_run` gains `undecodable` and `fidelity_fallback` (F11).
*Why it stops here.* The change moves `Manifest.UndecodableCount` (and `Result.Undecodable`), so it edits existing MA-348 assertions: `state/parsegap_test.go:67` (`UndecodableCount == 4`, which counts record e, a fallback + unparsed record, so it becomes 3), `app/undecodable_result_test.go:26` (`r.Undecodable != 3`, k4 is a fallback record, so 2), and the skipped encoder `health/undecodable_known_test.go`, which is written at the `Input` level (Undecodable 2, FidelityFallback 2) and would have to be rewritten at the manifest level. The `health`, CLI and GUI tests pin the sentences, which this proposal does not change, and their inputs set the numbers directly, so they stay green. Per the brief, no assertion was edited and nothing was built; the prove-fail would be: mutate the new counter back to "any parse gap" and watch the rewritten encoder go red.

**F3 · [Type III · in scope · cells OW-3, OW-11, CA-2] The counts overlap and the missing-content remedy is for a different source.**
`status` and the summary print "4 still missing content" and "7 … cannot decode" for 10 messages; the manifest test states the overlap is intended (a fillable parse gap is both). The remedy printed under it, "Missing content usually means it isn't cached locally (IMAP / a limited Outlook offline window). In your mail app, download for offline use, then simply re-run", is for a message the source has not delivered; here it is shown for a mailbox file the run read in full and found damaged.
*Change:* where a fillable record is also a parse gap, say so once ("… 4 still missing content (3 of them also counted below)"), and give a local file source its own remedy: "replace the damaged mailbox file with a complete export (the next run fills the message); nothing is lost meanwhile: what could be read is in the zip".

**F4 · [Type II · in scope · cells OW-11, OW-3 · MC20, by design] A message that cannot be completed keeps the posture WARN with no way to clear it.**
`unsplit-multipart` (and `corrupt-part`) from a local file are fillable, per MA-348 and MC20. In the walk the WARN, the `re-examined=N` and the unchanged text repeat every run. For a custodian polling `status -json`, `incomplete_content` never clears; for the owner there is no accept.
*Options (owner decision):* (a) keep as is and say in the WARN that a boundary-less message "stays listed until a complete copy is archived"; (b) class a local-file parse gap terminal (kept as received, nothing to wait for) while the run still re-reads it and fills it if the bytes change, as OW-3 showed it does; the class would then drive only the posture. (b) changes MC20's "permanent fillable by design" and MA-348's text, so it is not done here.

**F5 · [Type III · in scope · cell OW-10] A message whose text sits only in a structure-limit part also gets a fillable `missing-body` row.**
Archive F: the readable text is in `remaining-parts.undecoded`, the row says "download the message in your mail app, then run again; the original is kept", the run summary counts "1 still missing content" forever.
*Change:* when a `structure-limit` or `undecoded-part` part holds the message's text, do not add `missing-body`, or class it terminal with "the text is in the attachments zip as `remaining-parts.undecoded`".

**F6 · [Type III · in scope · cell CA-3] The `corrupt-part` why and remedy describe an attachment, whatever was cut.**
`RecordRowWhy`/`RecordRowRemedy` say "only the readable start is kept, under a name ending .partial" and "the readable start is in the attachments zip (its name ends .partial)". For a cut or mislabelled body (the row's own detail says "the text of part 1 … the readable start is shown") there is no `.partial` and no zip. Even with F1 decided, a damaged body will reach this row.
*Change:* split the sentence on whether the detail names a body: "the page shows the readable start of the text; the whole message is at the source".

**F7 · [Type III · in scope · cell IN-1 · design puts the README note with S7] `README.txt` and README.md contradict what this branch keeps.**

*Change (exact sentences):* in `README.txt`, after the row classes: "A file ending .undecoded was kept exactly as the message carried it, because this program could not decode its encoding (the report row names it, for example x-uuencode; a program that knows the encoding can open it).
