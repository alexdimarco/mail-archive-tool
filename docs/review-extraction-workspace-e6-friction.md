**Rationale.** What held up. The happy path is short and honest: tick Extract attachments, leave "One zip per message" selected, preview, start; 5 messages with 2 to 3 attachments each gave 5 zips beside their originals, one `README.txt` line saying so, and `unzip`, `ditto` and Python read every zip the tool made with the right names, the message's own date as the entry time and a 0644 mode (the E6Z-AO1 fix holds on this Mac: an accented name, a name with an en dash, and 27 hostile names extracted in full). The option is off by default, remembered when used, and the way (zip or loose) is remembered only by a start that used it. A retry of a failed message in zip mode makes its zip in part 2. What failed is the road after the first problem. (1) A run stopped while a message's attachments were being made (Cancel, a destination that fills, a record disk that fills) counts that message as exported, with no zip, a manifest note that says "export this message again" and no button that does it; "Export the remaining messages" skips it, and after that retry the card reads "Cancelled — the rest was exported in a later part of this set" and part 2 is "Complete": the set looks whole and one message's attachments are gone (F1). ## Findings

Blockers first (F1, F2), then the rest, most valuable first. "In scope" is this branch's. Each finding says what the walk saw and a suggested remedy.

**F1 · [Type II · HIGH · in scope · C8, C9, C11] A message whose attachments were stopped is counted exported, and the retry never makes them.**
When the run is stopped while a message's attachments are being made (Cancel, the destination filling, the record disk filling) the message stays `exported` with its original and page, the zip is discarded (zip mode, whole or not at all) or the folder is left part-filled (loose), and a note says "export this message again". "Export the remaining messages" retries only the messages not attempted, and "Export failed messages again" only the failed; this message is neither. Walked: Cancel at 250 ms, 600 ms (`s6-zip-250ms`, `s6-zip-600ms`: message 2 and message 4), retried (`s6b-retry`): part 2 is "Complete", part 1's card becomes "Cancelled — the rest was exported in a later part of this set" with Open folder and Check this export only. The only trace is the note in part 1's manifest and README line "Messages with an attachment that was not extracted, or only part of it: 1". A cautious owner who reads the cards believes the set is whole. The same holds for the destination that fills (`s7-dynamic-*`) and for the record disk (`s7-state`). The notes' words are right ("export this message again"); the way to do it is "select that message again in a new export", which nothing says. *Suggested:* (a) a message stopped in the making of its attachments is listed as not attempted (retryable), so "Export the remaining messages" takes it and the zip is made; or (b) the card of a stopped or cancelled export says "N messages were exported without their attachments: select them again, or see the README"; or both. (a) changes what "exported" counts for a message and what a retry takes, so it is the owner's; (b) is wording.

**F2 · [Type II root, Type III remedy · HIGH · in scope · C13, C17] A no-original record's zip is copied as the archive wrote it, and macOS `unzip` stops on it.**
MA-534 and the ruling say the archive's own `-attachments.zip` is copied byte-exact in zip mode. The archive's writer makes DOS-host entries (`creator=0`, mode `-rw-rw-rw-`, a zero date shown as `00-00-1980`) with a UTF-8 flag; macOS's `unzip` reads such a name as CP437, makes it under a mangled name and stops at the first one ("write error (disk full?)", exit 50), exactly the failure E6Z-AO1 fixed for the zips this tool makes. In `s8-archive-zip-dest` the archive's zip of four attachments (two ASCII, `Rapport février – final.pdf`, `日本語.txt`) extracted 2 of 4 under `unzip`; `ditto -x -k` and Python read it. A message from a French, Japanese or Polish sender is not rare. The README tells the inheritor "as the archive kept it" and nothing about this; the preview says "copied as it is". In loose mode the same record comes out in full (the export reads the zip with Go's reader and writes real files), so zip mode, the default, is worse for this record than the mode it replaced. *Suggested:* (a) a README sentence (and the Caveats line about an archived zip) saying that a zip copied from the archive may not open with the `unzip` command on macOS when a name has accented or non-Latin letters, and that double-clicking it in Finder, `ditto -x -k <zip> <folder>`, 7-Zip or Python reads it; this is words only and buildable now; (b) rewriting the zip's headers while keeping every entry's data (a new file, not the archive's bytes) or extracting the entries as loose mode does for this one record: both change MA-534's "byte-exact" and are the owner's.

**F3 · [Type III · in scope · C1, C2, C6, C7] The result card, the progress line and Export activity say nothing about attachments.**
A run with four messages carrying attachment notes ends "Complete · 5 exported" (`s5-zip`); the counts and the notes are only in `README.txt` and `export-manifest.json`. The README line is good ("Messages with an attachment that was not extracted, or only part of it: 4 … Each has a note …"); the window the owner looks at is not. *Suggested:* a second line on the card (and the progress "last") when Extract attachments was on: "Attachments: 12 attachments in 4 zips; 4 messages have a note — open the README" (and, with F1, the stopped count). The README's wording can be the card's.

**F4 · [Type III · in scope · C17] A Microsoft 365 export's README talks about the archive.**
In zip mode the bullet "A .attachments.zip is made by MailArchive from the .eml…" ends "Where the archive kept no original, the archive's own -attachments.zip, described above, holds the attachments, copied as the archive kept it, and no second zip is made", and the Caveats line "An archived attachments zip, copied as it is, is as the archive kept it … a message forwarded as an attachment inside an Outlook data file (.pst)…" is printed for every zip-mode export. Neither refers to anything in a Microsoft 365 export ("described above" is dangling; there is no archive). The loose bullet has the same "(or, where the archive kept no original, from the archived attachments zip)". *Suggested:* print those sentences only when the source is an archive and some message has no original, as the archive's "Extract attachments: … copied as it is" line already is.

**F5 · [Type III · in scope (text pre-dates this range) · C6, C16] The readable page sends the reader to a file an export does not have.**
For a part kept as received or cut short the page adds "The file attachments-report.tsv, in the archive's top folder, says which part and why" (`internal/export/html.go`, the archive's page text). **F6 · [Type III · in scope · C2, C6, C16] The page's list of names is not always the list of what is on disk.**
Zip mode took the page's names from the zip (E6Z-AI1), but a part that was not written (an empty one) is still listed as `empty.txt` beside "download zip", and nothing marks it; in loose mode the page lists the sender's name (`attachment-4`, `../../outside.txt`) where the file is `attachment-4.pdf`, `outside.txt` (the bidi half is ESC-E6Z-AO4, owner). *Suggested:* the page marks a part with no file ("not extracted: it had no content") and loose mode takes the same on-disk names as zip mode does.
