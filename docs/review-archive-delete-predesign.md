**Hidden blocker found by the rescue (no lens raised it as such):** the design's promise that a deleted archive stays deleted depends on finding every schedule, and it cannot. A schedule on *another computer* backing up the same USB or network folder, or any entry discovery cannot resolve, still fires afterwards. `app.RequireExistingOut` (`run.go:1414-1419`) checks only that the folder exists. So when the folder was kept because it holds the person's files, that run silently rebuilds a full archive in the folder just reported as "Deleted". → **C12.**

## Verdict: GO_WITH_CONDITIONS

No re-design is needed: every blocker and high has a named, modest change. Each condition below is a change to `docs/design-archive-delete.md`. All must be made, and re-verified against the findings listed, before code.

1. **C1 Lock order (§3, §4, §5).** Write the sequence: take the lock and re-check; remove every archive file except `.mailarchive.lock`, with the manifest or vault last; release the lock; remove `.mailarchive.lock` by exact name, retrying a few times; remove the folder. A lock file nobody holds never counts as "something of the archive left"; if it cannot be removed, the result says so and the delete is still complete. Add a Windows lab test: lock file and folder both gone. (L3-7-01, L5-8-01, L6-9-09)
2. **C2 Step order and recovery (§5, §5.7, §8).** New order: lock → schedules → per-archive config files → settings (Out, BackupFor) → scratch (C7) → folder contents, manifest or vault last → unlock + lock file (C1) → keyring (C8) → row → log. deletions.log gets a durable "started" line before the first removal and a "finished complete/partial" line after every attempt, so a partial or crashed delete is always recorded. A "started" line with no "finished" line for a path shows the row as "Delete not finished: click Delete again" in place of Switch, Run now and Archive now. A re-run is allowed even when the folder is gone or no longer an archive, for the config-side steps only. The panel says the log is kept and what it records. (L3-7-02, L3-7-03, L3-7-11, L3-7-12, L4-10-07, L1-2-10)
3. **C3 Remove from this list (§2, §5, §7).** Before acting, look up this folder's schedules in this computer's own records (job files with the same Out under SameArchivePath, DefaultNameFor and -verify entries, and recorded names when the folder is reachable). If any are found, the in-row question names them ("Its scheduled backup NAME will also be stopped") and Yes stops them with `RemoveLiveEntry` plus their job and config files. This works with the drive unplugged. Allow Remove on the current archive when its folder is unreachable or no longer an archive: it clears Out ("No archive chosen yet"). Every refusal names a step the person can actually take. Rewrite §2's "never changes schedules". (L1-2-01, L1-2-02, L4-10-02, L4-10-04, L5-8-12)
4. **C4 BackupFor (§5.1, §5.4, §7).** (a) When BackupFor names X and X is not current, Delete of X is refused with the true reason and remedy: the current archive Y's backup is registered under X's name, so remove it and set it up again in Settings. (b) The Remove refusal gives the same true reason. (c) Deleting the current archive removes both the entry named for Out and the one named for BackupFor (as `removeTasks` does) and clears BackupFor. One MA row for each case. Answers Q4. (L4-10-01, L5-8-03)
5. **C5 Three kinds of leftover (§4, §8).** (a) A name the archive recorded or owns that could not be removed blocks the manifest or vault: "Not fully deleted". (b) OS litter *files* (IsLitter) are removed in every folder the archive owns. A litter *folder* is never cleared, and it keeps its parent folder. (c) Anything else is kept and listed as "kept: not the archive's". It never blocks completion. Completion means no recorded name remains. The remedy follows the error type: a sharing violation gets "close the program"; access denied gets "Windows security or antivirus blocked it: allow MailArchive or delete by hand"; a device that has gone gets "reconnect the drive". A briefly busy empty folder is retried before it is reported. Tests: .DS_Store or desktop.ini in a store subfolder, and a person's file in a store folder, both end "Deleted". (L3-7-04, L4-10-03, L5-8-06, L1-2-03, L4-10-14, L3-7-13, L6-9-11)
6. **C6 Schedule discovery (§3, §5.1, §5.3).** A read-only step before the lock lists every entry for the folder: DefaultNameFor and -verify; RecordedBackupName and RecordedVerifyName, read first; job files whose Out matches under SameArchivePath (finds other spellings); and OurInstalled entries whose -out names it. The plan shows them all. Step 1 removes each one, and step 3 removes each name's job file, jobfail logs, alert-streak and sync-alert, its `last-failure.json` match, and `<name>.log` / `<name>.stderr.log`. When a descriptor is unreadable or names an entry bound.go refuses, Delete is refused before anything changes, with the by-name remedy. A custom name that cannot be proven from the scheduler's own definition is listed in the plan as "not removed: check it yourself". Each scheduler call has a time limit. Tests: a custom -name, two -name installs, another spelling, a legacy verify, a denied or hung scheduler. (L3-7-05, L5-8-04, L6-9-05, L6-9-10)
