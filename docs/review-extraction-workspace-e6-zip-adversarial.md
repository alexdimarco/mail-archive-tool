## Behaviour changes the owner should know

None narrows a guarantee a row states; each follows the finding's own remedy.

- **Zip entries are made on a Unix host with mode 0644** (E6Z-AO1): the owner's extracted files are readable by the user and group and not writable by others, as a Python or `zip` file would be. The zip is still the same bytes every time for the same message.
- **A zip that is stopped or fails is gone whole, and says so once** (E6Z-AO2): the one note says no zip was written and all N attachments were not extracted; the per-part notes made for that zip (an empty part, a part kept as received) are dropped with it. A zip that is placed keeps every note it had.
- **A stop during the flush discards the finished zip** (E6Z-AC3), for Cancel as well as Abandon.
- **A part within about 0.2% plus 5 KB of the free space is a "no space" note** (E6Z-AC1) where it was tried before; the earlier entries stay.
- **Entry times outside 1980-01-01 to 2106-02-06 UTC are the epoch** (E6Z-AO6), as a message with no date already was.
- **An attachment name over 255 bytes loses a trailing space or dot its extension cut can leave** (E6Z-AO5), in the export-only pass shared with loose mode; such a name is a different name than before.
- **The readable page names an attachment by its entry in the zip** (E6Z-AI1), so a duplicate is listed as `dup.txt (2)` and a leading dash or tilde has its underscore.
- **README of a zip-mode export that holds only archive zips says so** (E6Z-AI2).

## What held (the finders tried and failed)

- Name containment: `../`, absolute, drive letters, UNC, backslashes, NUL, `:` streams, leading dot, device names with an extension or trailing spaces, COM superscripts, case, NFC/NFD and ß duplicates, 8.3 aliases and percent-encoded and RFC 2231/2047 names all end as one flat segment under Python `extractall`, macOS `unzip` and `bsdtar`.
- Zip metadata: no directory entries, no symlink flag, no encrypted flag, no zip comment, only the 0x5455 timestamp extra, the entry date is the message's own, and the same message gave the same zip bytes twice (still so after the host byte and mode were set).
- A zip is renamed into place only after `Close`, `Sync` and `Close`; a kill leaves at most a `.mailexport-*.tmp` (the accepted W6 class), never a torn zip under a final name, and the run record's line is appended only after the rename.
- Memory: a part is buffered whole, one at a time, bounded by the 256 MiB MIME cap; Zip64 for a part over 4 GiB cannot occur; entry counts above 65,535 do occur (E6Z-AO3) and read back fine.
- The archive-zip byte-exact path: a planted or changed zip fails the message as changed, a symlink or hard link is refused, the temp-and-no-replace rename never replaces a planted file, and with no original the archive's zip is copied as it is (MA-534) and never read or expanded.
- Hashing and role correctness: the record's size and SHA-256 come from the hash writer over the bytes written; tampering with a derived zip gives the derived-file RED with its remedy; the archived zip is never demoted.
- Manifest, report and sums text: hostile names pass through `ExportFilename` and `plainText` with `%q` and the 20-note cap; the page's link is `url.PathEscape` of a name built from the stem, so there is no path injection.
- Disk-full, Cancel at the zip's creation, a part stream that fails or panics (recovered by `guardStream`) and ENOSPC on every zip write across 60 messages: no residue, no fd or goroutine growth.
- Plan sizing does not starve later originals (`derivedBudget` holds back their size hints, E6-AI4); loose-mode behaviour is unchanged (`TestLooseModeIsUnchangedByTheZipModeSwitch`); `vet` and the Windows test build are clean.

## What this round did not cover

- **A fresh check of these fixes.** They were red-then-green by their fixer, who did not find the findings, and E6Z-AO1 was also run on the real macOS `unzip`; nobody else has re-read them. The new code on the writer's path (`attachZipHeader`, the note mark in `zipParts`, the stricter room, `Attachment.ZipName` into the page) is owed that look before the option is revealed.
- Windows and macOS runs: Windows Explorer and 7-zip extraction of the new host byte and mode, Archive Utility, a Windows best-fit unzip (E6Z-AO7), an HFS+ volume (E6Z-AO7), and the Windows sharing-violation retry in `placeRetry` (a Cancel during it would report "context canceled" as a write failure, as loose `put()` does).
- The room estimate is `len/512` of a part, about six times what deflate costs on noise; it was kept because it is the design's number and `used` already counts it, not tuned. Zip64 for a part over 4 GiB is not reachable under the 256 MiB MIME cap and was not run.
- The sentence on the readable page that sends the reader to `attachments-report.tsv` in the archive's top folder (E6Z-AI1) was not verified and is the same text in loose mode.
- One antivirus-flagged part quarantining the whole zip (the finders' observation: a message loses all its derived attachments and the page keeps a dangling "download zip" link) was not run.
- A kill mid-zip leaves the `.mailexport-*.tmp` and no sweeper removes it (the same for originals and loose files; Check flags it as unlisted): the accepted W6 class, not new.
- The 1.43 plan-sizing ratio (E6Z-AC4) and the skeptic's other figures were not re-measured by the fixer.
