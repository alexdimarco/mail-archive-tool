# Adversarial review: extraction workspace archive source (EW-E4 addendum)

29 found / 20 confirmed / 2 refuted. The other 7 are set aside separately: 6 duplicates (E4-AO8, E4-AI3, E4-AC1, E4-AC2, E4-AC4 and E4-AC9, each of a finding that is also in the table) and 1 non-goal (E4-AI11). Of the 20 confirmed, 18 are fixed and 2 are open (E4-AO5, E4-AI10), each with a skip encoder.

**Verdict: FINDINGS OPEN.** Two confirmed findings are unfixed because their fixes need an owner decision: **E4-AO5** (medium: the 1 GiB R-o4 cap bounds a manifest's bytes, not its memory; a manifest of bare records costs 22 to 34 times its size, once for the snapshot and again for the copy Changed reads) and **E4-AI10** (low: an attachment named "unknown", "body" or "unparsed" is stored as the state layer's own gap label, so a real gap is worded as an old-version caveat). The other 18 confirmed findings are fixed, each with a tombstone that was seen red against the unfixed code and is green now; two of them are fixed in part and say so (E4-AC5: the list now discloses that the archive changed, and paging stays offset-based; E4-AI1: a Settings save while an export is running is not covered). Nothing refuted or set aside is open. The Windows legs (E4-AO1's UNC lookup, E4-AI9's share mode) are read from code and compiled, never run, so they are verified on macOS only. Two known items (K1, K2) were test gaps and have their tests, each red against a mutation. No second check of the fixes by another agent has been done yet.

## Escalations

Both need an owner decision, and neither was fixed. Each carries a skip encoder whose body is the assertion the fix must satisfy (red today with the Skip taken out, run in a detached probe worktree).

- **E4-AO5** (medium; also E4-AC2 and the manifest half of E4-AI3). RR2-C11 and MA-512 fix the R-o4 cap at 1 GiB of bytes, and MA-531 says "no unbounded allocation"; a manifest's memory is not its bytes (22 to 34 times for bare records, 1.6 times for a realistic manifest), so a dense manifest under the cap handed over as another archive folder can hold tens of GiB, once for the snapshot and once more for the copy Changed reads during a run, and Go's out-of-memory is fatal. The remedy is a limit that is not the byte count: a record count (or a cost per record) with its own R-o4 wording, a lower byte cap, or both. The number and the wording are a ruling's, so nothing was changed. A starting point for the owner: refuse, with R-o4's remedy ("make it the archive location in Settings"), a manifest of more than 2,000,000 records (an estimate, not measured: a realistic record is some 700 bytes, so a realistic 1 GiB manifest holds on the order of a million and a half), and read the version before the full unmarshal. Skip encoder: TestAnotherArchiveFolderManifestMemoryIsBoundedBySomethingBesidesItsBytes (MA-531, MA-512, R29, S52).
- **E4-AI10** (low). A gap label is the attachment's file name, so an attachment named "unknown", "body" or "unparsed" is stored as a state-layer sentinel, and the archive source's export words a real current gap as "completeness was not tracked by the version that captured this message". The MA-435 test pins that wording and forbids the literal in it, and MA-355 treats these names as ambiguous on the capture side, so the note builder cannot resolve it. The remedy is a label for a real attachment that no sentinel can equal (for example "attachment: unknown"), which changes what a manifest records and how the capture side matches labels. Skip encoder: TestAnAttachmentNamedLikeASentinelHasALabelThatIsNotOne in internal/export (MA-355, MA-435, R28, R20).
