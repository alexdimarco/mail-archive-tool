## What held

The finders tried these and they held (several were re-run in this round):

- Walk, depth and cycle guards: cycle and over-depth rows are caught and recursion is bounded. XOR 0xFF and XOR 0x01 at every one of the 1,033,216 offsets of `support.pst`: no escaped panic, no crash, no walk over 6 s (the silent-loss offsets of the XOR 0x01 sweep are the K7 family, now covered).
- Inward recovers: `readSubFolderRows`, `parseSubFolderRow`, `readRow`, `readEnvelope`, `readBody`, `readCategories` and the attachments guard contained every panic seen; no go-pst panic left the walk. 206,588 single-byte mutations of `support.pst`, each walked and every attachment written to a discard writer: zero panics before this round's attachment trigger was built by hand.
- Store uid: a missing, zero or over-long uid falls back to the per-folder aggregate; the ledger key includes the token, so two files with a duplicate uid do not cross-recover.
- Row breaker on message tables (invalid, duplicate and absent NIDs aggregate and stop at 100); message-subject file names stay inside the path budget; the report TSV and the ledger strings are stripped at ObserveGap, Load and the TSV writer.
- Legacy-placeholder re-class against crafted records (key shape, folder names cannot shift the identity component, a PST item is Terminal, not Missing, so a hostile subject cannot use it to hide a PST gap).
- Outlook skip gaps are ledger-sanitized; a hostile ledger on Load (control characters, bidi, unknown class, unknown scope, tokens not in Stores).
- MA-319's store-uid rule (an old-uid gap is closed by absence when another store sits at the same path; never recovered by a same-NID message). Same file by two spellings in one run. A walk aborted by a cancel, a lost lock, a run-fatal error or a store-level error closes nothing. `-since` retains export-stage and older item gaps. The KEEP guard runs in both modes before any write.
- A symlink or junction under `-out` is written through (existing behaviour); the probe's lock check catches a vanished volume.
- The BeforeWrite seam and the typed `FolderError`, `ItemError` and `ErrUnsafeToken`: every return of Export is typed or nil.
- No data race: `go test -race` over source, app, export and state was clean for the finders and is re-run below. The walk, the fault callback, the checkpoint and the manifest save run on one goroutine.
- Cancellation mid-walk keeps both seeded gaps and closes none; writes are atomic and ordered (temp file plus rename; zip, then page, then Manifest.Add, then OnExported); the checkpoint is fault-driven and its lock re-check stops the run before any shared write; the breaker count, reset and probe pacing behave as documented; 100,000 distinct item gaps cost 1.5 s through the lifetime caps.
- Lock ordering: `manifest.mu` is a leaf lock; `CloseUnobserved` calls the guard under it and the guard touches only the source run's state (this round's `GapObservedIn` and `CloseGapInFolder` take the same lock and call nothing back).
- A volume-full error during `WriteZip` is swallowed (logged, the attachments recorded as attachment-error, fillable) so the run keeps archiving attachment-less pages until a page write fails: visible and heals on the next run; held, not reported.
