# Friction review — FI-S1a: fault isolation, sinks and surfaces

> As of 2026-10-10, walked against `wip/fi-s1a` at `dce061e` (change set
> `46e7de6..HEAD`, catalog rows MA-323, MA-326..MA-329, scenarios S46 and S48) with
> the built CLI on macOS, plus the CLI built from `46e7de6` (the tree before the
> branch) for the mixed-version cells. Method: the assurance-kit friction review,
> each cell an actor × scenario walked by typing the commands and reading the
> output, classified Type I (the ceremony is the control), Type II (design choice,
> reducible without weakening the control), Type III (missing legibility or
> tooling). Every command ran with HOME and the per-user config folders in a
> scratch home; scratch archives came from a small synthetic mbox, no real mail, no
> network, no scheduler. **No producer records a ledger gap yet** (S2a and S3 build
> them), so the ledger was **seeded**: a Python driver copied a real archive, wrote
> `capture_gaps` entries, `stores` ids and a last-run record in the shape
> `internal/state/gaps_test.go` and `internal/app/gaps_surface_test.go` use, and
> then ran the real binary (`reindex`, `status`, `status -json`, `verify`,
> `verify -json`) over it. The report, the root page and the banner in this report
> are the real output of those commands. The run summary's "Not captured" block and
> a real partial run cannot be produced by the binary yet (a real run closes or
> never creates a seeded gap), so those two are reasoned from the code and its tests
> and said so in their cells. This file was filed with no fixes.

**Cells walked:** 18 &nbsp;·&nbsp; **Functioning as walked:** 5 yes / 13 partial / 0 no &nbsp;·&nbsp; **High-friction cells:** 3 (OP-5, CU-1, IN-1) &nbsp;·&nbsp; **Findings:** 19 — Type I: 2 · Type II: 3 (1 in scope) · Type III: 14 (13 in scope, 1 out of scope)

**Verdict: SHIPPABLE** (design verdict), contingent on the in-scope Type III operability backlog below being built before merge, led by F1, F2, F3 and F8, which account for the three high-friction cells. No Type II finding rises to a usability regression: the two largest (a partial run recorded as `failed`, and a not-attempted gap shown only as a note) are owner rulings with a named follow-up (S1b, OR3), and the third (F14) is a wording fix away from honest.

**Rationale.** The mechanisms hold up under the real binary. A healthy archive is untouched: `status` and `verify` print byte-for-byte what the pre-branch binary prints, the root page has no banner, and `status -json` only gains the two additive keys. A seeded ledger reaches every surface the rows promise: stuck is a WARN listed first, never RED; a not-attempted gap is a note ("never captured, last attempted ..."); the cap holds at 20 lines; the report has one row per gap with the source id; the banner appears on the root page after `reindex` and is stamped with the count; `verify` keeps its verdict and exit code and adds its line; hostile subjects, folders, reasons and source paths lose their control characters on every surface (no ESC, no CR, no LF in `status`, `verify`, `-json`, the TSV or the page). Old and new binaries read each other's archives without error.

The friction is in how the surfaces tell the actor what to do. The one remedy this branch adds to a real failure today, the in-place `.pst` repair, is attached to every `.pst` open error by file extension, including "permission denied", and it exists only in the run log: `status`, the attention file and the last-run record say "1 file(s) failed" and nothing else (F1, F2). The gap list under `status` is in ledger order, not severity, so past 20 entries the stuck item is counted but neither listed nor in `-json` (F3). The README's `status -json` contract was not extended, so a custodian cannot learn the new keys or codes except by running the command (F8). The inheritor's way from the banner to a remedy has a dead end: the report is named, not linked, carries reason codes and no remedy, and nothing cold names `mailarchive status` (F10). All are buildable-away and in this branch's own surfaces; none changes a control.

## Findings

In this branch's scope first, most valuable first; then the out-of-scope items.

**F1 · [Type III · in scope · cell OP-5] `dataFileRemedy` attaches the repair advice to every `.pst` error by extension.**
`internal/app/run.go` `dataFileRemedy` returns " — a damaged .pst can usually be repaired: repair the file in place with Outlook's Inbox Repair Tool (scanpst.exe …)" for any error on a path ending `.pst`. Walked: a `.pst` with mode 000 prints "…permission denied — a damaged .pst can usually be repaired: repair the file in place …", and the same for an empty file ("failed to read signature: EOF", fair) and a junk file ("unsupported format type", fair). Fixing permissions is the remedy for the first, and a repair tool run on a locked or unreadable file cannot help. The errno classifier `state.GapErrnoClass` already exists and `GapRemedy` uses it for `file-unreadable`.
*Change:* key the `.pst` line by the cause (permission or in-use: fix the permissions, close Outlook; a parse or format error: the repair), as the ledger's remedy table does.

**F2 · [Type III · in scope · cells OP-5, OW-1] The one remedy this branch adds to a real failure is visible only in the run log.**
A `.pst` that fails to open is a run failure today ("1 file(s) failed"), not a ledger gap. The run log's error line carries the file and the remedy. The last-run record, `status` ("RED: the last run … FAILED: 1 file(s) failed"), `status -json`'s `last_run.error` and `BACKUP-NEEDS-ATTENTION.txt` carry only "1 file(s) failed", and the sidecar tells the reader to run `status` "for the full posture and the remedy". `status` then names neither the file nor a remedy. An owner or a custodian is sent in a circle, and the scheduled job's `-log` is the one place the answer is.
*Change:* carry the failing path and the one-line remedy into the run's returned error (and so the record and the sidecar), or give `status` a `run_failed` remedy for a recorded file failure. (S2a will make an unreadable `.pst` a ledger gap whose remedy `status` prints; this closes the interval and the case where no gap is recorded.)

**F3 · [Type III · in scope · cells OP-2, CU-1] The gap list is in ledger order, so a stuck item can be counted but not listed.**
`gapLines` and `jsonCaptureGaps` take the first 20 gaps in the ledger's stable order (source, folder, reason, locator). Walked: 25 fillable items in "Inbox" and one stuck item in "Zeta" give `capture_gaps.stuck: 1`, the stuck WARN, and 20 lines and 20 JSON items none of which is the stuck one (the `stuck` flag exists on the items, so a script could find it if it were listed). A stuck line is also not marked: the only difference between its line and an ordinary one is the remedy text.
*Change:* sort the listed gaps stuck first, then terminal, then fillable, then not attempted, before the cap; mark a stuck line ("stuck since …"). The same order for `+N more`.

**F4 · [Type III · in scope · cells OP-1, OP-2, OP-3] The WARN headline repeats and glues remedies.**
`remedyFor` joins up to three distinct remedies with "; ". Walked: the fillable WARN repeats "retried" three times ("they are retried whenever the archive runs again … — it is retried when you run again; check the network …; it is retried when you run again"); the terminal WARN of `a3` is one line of three long remedies each holding its own "; " and " — ", with no source named; the overflow remedy reads "see the report; fix the cause of the first failures, then run again; it is retried when you run again" (contradictory in tone). The stuck headline says "have failed on every run since", which reads as a run failure; the items were not captured.
*Change:* the headline says what and how many and where the list is; each remedy appears once, on its own line (they already do); at most one remedy per source kind in the headline, labelled; reword "failed on every run" to "have not been captured on any run since".

**F5 · [Type III · in scope · cell OP-4] "+N more" counts ledger entries and the capped lines hide the report's path.**
`gapLines` reports `len(gaps)-20`, which is entries; the headline's 4025 and `verify`'s 4035 are items (an overflow entry stands for 4000). "+16 more — see the report" under "4025 item(s)" does not add up. The report path is in the fillable WARN only; a terminal-only archive's "+N more — see the report" has no path.
*Change:* "+N more (M item(s)) — see <path>", with the same words in the run summary's own "+N more".

**F6 · [Type III · in scope · cells OW-1, CU-1] `Incomplete: none` beside "NOT in this archive".**
The `Incomplete:` line and `-json`'s `fillable`/`terminal`/`unknown` count records; the ledger's items are a separate tally under the WARN. An owner scanning the top block sees "Messages: 6 · Incomplete: none" and a WARN at the bottom; a custodian sees `fillable: 0` beside `capture_gaps.fillable: 2`.
*Change:* a "Not captured:" line next to "Partly read:" (the branch already added that precedent) with the class split and the report path, and a README sentence that the two counts are different things.

**F7 · [Type III · in scope · cell OW-4] An unparsed record is described two ways, and a partly-read one is never named in `status`.**
Seeded `unreadable:attachments` and `unparsed` records print "Incomplete: 0 still missing content · 1 source-empty (never fillable)" (an unparsed record counted as source-empty) and "Partly read: 1 message(s) could only be partly read (see the posture below)", while the note says the unparsed one is "kept as raw text"; JSON `terminal: 1` and `fillable: 1` (records) next to `unreadable: 1`. No `status` line says which message. `Result.Fillable` was changed to leave partly-read records out; `Counts()` was not, so the two surfaces disagree.
*Change:* subtract partly-read and unparsed records from `Incomplete`'s lines the same way `Result.Fillable` does, and list their pages (the 20-line list) or name the report.

**F8 · [Type III · in scope · cell CU-1] The `status -json` contract in `README.md` was not extended.**
g7's friction report made `README.md`'s Machine-readable output section the custodian's contract (F8, F15 there). This branch adds `capture_gaps {fillable, terminal, info, stuck, not_attempted, oldest_first_run, items[<=20 {source, folder, subject, date, scope, reason, class, remedy, runs, attempted, stuck}]}`, `unreadable`, `last_run.gaps_observed|gaps_new|gaps_recovered|gaps_fillable|gaps_terminal|gaps_stuck|unreadable`, the codes `capture_gaps_stuck`, `capture_gaps_fillable`, `capture_gaps_terminal`, `capture_gaps_not_attempted`, `unreadable_messages`, `unparsed_messages`, and `verify -json`'s `gap_items`/`gap_folders` (omitted when zero, unlike `status`, which always emits `capture_gaps`). None is in `README.md` (`git diff 46e7de6..HEAD -- README.md` is empty), whose code list is stated as "the codes:". A monitor author cannot write a gate on `gaps_new` or `capture_gaps_stuck` from the docs.
*Change:* document the keys, the codes, which counts are ledger and which are records (F6), that `last_run.gaps_*` are omitted on an older record, and that an older build omits all of it.

**F9 · [Type III · in scope · cell OP-7] `verify`'s "Not in this archive" line does not separate retryable from needs-action and sits above "attested".**
"Not in this archive: N item(s), F folder(s) from the source could not be captured (see attachments-report.tsv) — this does not affect attestation" prints "0 folder(s)" when there are none, does not say how many will be retried, and ends by calling attestation what the next line then states ("attested: every recorded file was checked and intact"), which a skimmer reads as "complete". It is walked as honest about the verdict (exit 0, or 2 beside a modified file), but not about the archive.
*Change:* "N item(s) retryable, M need action"; omit zero parts; end the line "attested means the files held are intact, not that the archive is complete".

**F10 · [Type III · in scope · cell IN-1] The inheritor's path from banner to remedy has a dead end.**
Walked cold on `a3`: the banner names `attachments-report.tsv` in plain text (no link, no count); the TSV's `kind` is a reason code; the README defines the classes but neither the kinds nor the remedies, and has never named `mailarchive status`, where the remedy lives. The README's closing sentence (a fillable or terminal row is missing if no one runs the tool) is the right fact and is the only one an inheritor can act on without the CLI.
*Change:* make the banner's file name a relative link; add a plain-words "what it means" and the remedy to each report row (the table the surfaces already share, `state.GapWhy` and `GapRemedy`); name `mailarchive status -out .` in the README's paragraph.

**F11 · [Type III · in scope · cell OW-2] The Microsoft 365 deadline remedy is shown once, in a log.**
`gapSummaryLine` adds `GapDeadlineRemedy` on a fillable Graph gap's first sighting only, in the run summary. `status`, `status -json` and the report use `GapRemedy`, which has no deadline line, until the gap is stuck (3 runs and 72 h at least; two periods on a weekly schedule). An owner who is about to lose the mailbox and reads only `status` is told the item is retried.
*Change:* add the sentence to the fillable Graph WARN while any listed gap is Graph, or give the JSON item a `deadline` remedy.

**F12 · [Type III · in scope · cells OW-3, OP-3] No surface says whether the original still exists.**
"NOT in this archive and will not be without action" is true; whether the item still sits in the mailbox or file (nothing lost, only not archived) or the damaged `.pst` is the only copy (possibly lost) is stated by no WARN, line or banner, except the scratch `.pst`'s "it is still in your mailbox". *Change:* one clause per source kind in `GapWhy`/`GapRemedy`: mail server ("still in your mailbox"), local store ("still in the file"), `.pst` ("the only copy is the file; keep a copy of it before repairing").

**F13 · [Type II · out of scope (S1b) · cell OP-6] A partial run is a failed run.**
Ruled (OR1, OR2: S1a maps a partial run to `failed`, exit 1, RED; S1b adds the `partial` flag).
